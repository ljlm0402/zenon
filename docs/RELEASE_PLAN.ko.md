# 2.0.0 정식 릴리스 계획

작성 기준: 2026-10-18, Asia/Seoul(KST).

## 현재 상태와 범위

사용자 요청에 따라 RC 준비에서 정식 2.0.0 패치 준비로 전환했다. package.json과 package-lock.json은 2.0.0으로 일치한다. RC 게시·실제 앱 적용 기간을 완료했다고 간주하지 않는다. 기존 10월 20일 RC / 26일 정식 목표는 이전 제안이며, 정식 게시 시점은 아래 검증 및 게시 결정에 따른다. 자동 게시 예약은 없다.

정식 범위는 패키지 진입점·타입 정비, 상태 갱신과 오류 처리 안정화, 데이터 마이그레이션·원본 백업·복구 API, SSR context와 예제, 릴리스 채널 보호다. 저장 실패 기본 정책, 오류 처리 반환 타입과 compose 계약 변경 때문에 1.x 호환 패치가 아닌 메이저 버전으로 제공한다. [변경 및 이전 안내](./RELEASE_NOTES.ko.md)를 먼저 확인한다.

선택자 구독·자동 해제, 비동기 저장소, 자동 SSR hydration 및 직렬화는 이번 범위에 포함하지 않는다. 후속 차별화 전략은 [로드맵](./ROADMAP.ko.md)에 유지한다.

## 게시 전 조건

1. PR #11의 최종 커밋에서 리뷰와 CI를 완료하고 릴리스에 포함할 커밋을 확정한다. CI 성공은 리뷰·병합 완료를 의미하지 않는다.
2. npm run check, 예제 타입 검사·빌드, Vue 3.2.0 패키지 소비자 검사를 통과한다. 실제 tarball·소스 manifest·lockfile의 두 루트 버전이 모두 2.0.0인지 test:package에서 검사한다.
3. 대상 앱의 복사 데이터로 정상 복원, 이전 버전 변환, 손상·미래 버전 거부, 저장 실패 후 재시도, 백업 충돌을 확인한다. SPA 갱신·재마운트와 SSR 요청 격리, 해당 앱의 hydration 경로를 확인한다. 자동화된 패키지 테스트만으로 실제 앱 검증을 대체하지 않는다.
4. 게시 결정 후 확정 커밋에 v2.0.0 태그를 생성·push한다. 태그 push는 npm 게시 workflow를 실행하므로 점검 목적으로 push하지 않는다. 태그와 package.json 버전이 정확히 일치하고 모든 배포 검사를 통과해야 latest로 게시한다. prerelease 태그는 계속 next로 분리된다.

## 게시 후 확인 및 복구

- npm 레지스트리에서 2.0.0과 latest 채널을 확인한다. 소비 앱에는 zenon@2.0.0을 명시적으로 설치하고 이전 앱 버전·lockfile·사용자 저장 데이터 복사본을 보관한다.
- 실행 환경(Vue·Node·브라우저), 설치 버전, 재현 절차, 기대·실제 결과를 기록한다. 데이터 손실·요청 간 상태 공유·설치 실패가 발견되면 확산을 중단하고 수정 버전을 검증한다.
- 앱 롤백은 이전 앱 버전과 lockfile로 수행하되 변환된 저장 데이터를 이전 코드가 읽을 수 있는지 먼저 확인한다. 백업 복구가 필요하면 현재 데이터도 별도 보존하고 쓰기를 중단한 상태에서 앱별 복구 절차를 적용한다.
- npm 채널 변경이나 라이브러리 버전 하향만으로 저장 데이터는 복구되지 않는다. 백업/본문 쓰기는 다중 키 원자적 트랜잭션이 아니며 앱의 데이터 관리가 필요하다.

현재 Git 태그 생성·npm 게시·레지스트리 권한 검증은 수행하지 않았다. Node 22와 Vue 3.2.0·3.5.17의 자동화 검증 범위를 넘어선 전체 버전 조합 및 사용자 앱 적용 결과는 확인되지 않았다.
